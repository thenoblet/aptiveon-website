§ 03.1

How it works

4 phases · 12–16 weeks

One project per intern, end-to-end. You design it with a mentor, build it, put it in front of a real user, and write up what you learned.

01 / DESIGN

Scope & design

weeks 1–2

Pick a real problem with a real user. Write a one-page spec. Argue it with your mentor.

02 / BUILD

Build

weeks 3–10

Ship the system. Weekly demos, code review, paired sessions on the hard parts.

03 / DEPLOY

Deploy & observe

weeks 10–14

Put it in front of the real user. Watch it. Fix what breaks. Measure what matters.

04 / WRITE

Write it up

weeks 14–16

A public-quality writeup of what you built, why, and what you'd do differently.

§ 03.2

Project types

pick one, scope it down

Every intern project lands in one of these four buckets. The exact problem changes by cohort and partner — these are the shapes.

TYPE · ASSISTANT

A digital assistant for a real role

Pick a role, sit with someone in it for a day, build the assistant they actually need. Cite everything.

e.g. SOP assistant for ops · drafting tool for a writer · triage for a support queue
TYPE · RAG

A retrieval pipeline + eval harness

Build a grounded Q&A system over a real corpus. Write the evals. Beat your own baseline twice.

e.g. policy Q&A · technical-docs assistant · academic-paper retrieval
TYPE · WORKFLOW

An automation with human review

Take a manual workflow, automate the easy 80%, route the hard 20% to a human. Audit every run.

e.g. invoice extraction · doc routing · cross-system reconciliation
TYPE · APPLIED SYSTEMS

An internal tool that replaces a spreadsheet

Find a spreadsheet that ought to be a system. Build the system. Keep it boring.

e.g. ops dashboard · admin tool · partner intake portal
